# 解决问题 (Problem Solving)

> 本模块用于攻坚真实难题、排除系统故障根因、打破路径依赖。


## 第一性原理 (`first-principles`)
**定位**：别再打补丁了，拆回最底层重新推一遍

```markdown
我想解决的问题是：【填写你的问题】。

请用第一性原理把它拆回最底层，区分：
1. 已经确认、无法绕开的基本事实；
2. 习惯性接受、却没有验证过的假设；
3. 真正想实现的目标；
4. 现实中的资源与约束。

暂时放下行业惯例和现成方案，只从基本事实、目标和约束出发，重新推导可行路径。

最后请输出：
1. 原方案中只在修补表面的部分；
2. 从基本事实重新推导出的新路径；
3. 这条路径成立的前提；
4. 验证它的第一步。
```

## 跨领域借解 (`cross-domain-borrow`)
**定位**：你这个问题，别的行业可能十几年前就解决了

```markdown
我的困惑是：【说明背景、当前做法、现实约束和具体卡点】。

请先剥掉行业术语，把它抽象成一个人类在其他领域也可能遇到的问题，并找出：
1. 问题的底层结构；
2. 真正的核心矛盾；
3. 普通解法失效的原因。

然后从历史案例，以及至少3个彼此距离较远的领域中，寻找底层结构相似的问题。

每个案例都要说明：
1. 那个领域遇到了什么问题；
2. 使用了什么解决机制；
3. 与我的问题相似在哪里；
4. 哪些部分可以迁移；
5. 什么条件下会失效。

最后请选出最值得借用的3种机制，把它们翻译成适合我当前处境的解决方案，再推荐一个最值得先试的低成本、可逆实验。
```

## 五问法 (`five-whys`)
**定位**：失败了别急着找人背锅，一层层问为什么，挖到能改的系统原因

```markdown
这次出问题的事是：【写清楚出了什么事、什么时候、造成了什么后果】。
我已经知道的直接原因是：【写下你目前认定的那个直接原因】。

请陪我用五问法做一次复盘，目标是找到让这件事能发生的系统原因，不是找一个人来背锅。

规则：
1. 一次只问一个「为什么」，等我回答完再问下一个，不要一口气把五个都问完。
2. 每一层的回答都要能拿事实、记录或数据支撑。我给不出证据的，标成「待核实」，不要当成已知往下推。
3. 每一层都问一句：如果当时有人在，换一个人会不会还是出同样的错？会，就继续往流程、工具、信息、激励上挖；不会，再看是不是个人原因。
4. 如果某一层同时有好几个原因，分叉出来，每个分支单独往下问，不要只挑一个顺眼的。
5. 不一定刚好五层。挖到一个能改、改了这类事就不容易再发生的地方就停，不够就继续问。

问完之后请输出：
1. 一条从结果一路倒推到根因的因果链，每一环标明有证据还是待核实；
2. 根因清单，分成「流程」「工具」「信息」「激励」「个人」几类，没有的类别不写；
3. 每个根因配一个改进动作，写清楚谁来做、什么时候之前做完、怎么检查它真的生效了；
4. 一条最容易被大家略过、但最该改的根因，以及为什么容易被略过。
```

## 共性复盘 (`common-cause-retro`)
**定位**：把一段时间里的 Bug、返工、回滚和重复修改放在一起，找出共同根因

```markdown
全面复盘最近XX时间的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者Skill，避免我们反复支付同样的成本。
```

## 认知重评 (`cognitive-reappraisal`)
**定位**：被一句话困住的时候，把那句自动想法核一遍，写出更站得住的一句和一个小动作

```markdown
我现在卡住的情境是：【写清发生了什么、谁说了什么】。
我脑子里反复出现的那句话是：【自动冒出来的原句，不要修饰】。

请陪我做一次认知重评，把这句自动想法核一遍。这不是治疗。如果我提到伤害自己、不想活，或者难受已经严重到没法做这个记录，请停下来，告诉我去联系身边能帮忙的人，或者找专业的心理帮助，不要继续往下问。

规则：
1. 一次只问一个问题，等我回答完再问下一个，不要把整张记录一次倒给我。
2. 自动想法要原句。我说得含糊，就追问那句原话，不要替我改写成更体面的说法。
3. 证据只收我举得出的具体事实。我说「他们肯定觉得我差」却举不出事实，标成「这是猜测」，不要当成证据。
4. 思维偏差有就点名，没有就写没有。常见的有：全或无、灾难化、读心、过度概括、情绪推理、贴标签、应该句式、把什么都揽到自己身上、只看见负面。不要为了凑数硬套。

按这个顺序问：
1. 情境里还有哪一句事实我没说清。
2. 自动想法的原句，一个字不改地确认一遍。
3. 此刻的情绪叫什么，强度从 0 到 100，100 是最强。
4. 有哪些事实支持这句想法。
5. 有哪些事实反对这句想法。
6. 上面这些里，有没有思维偏差，有的话叫什么名字。
7. 请我写一句更平衡的替代想法。它要同时装得下支持和反对两边的事实，不要写成空洞的加油，也不要假装坏事没发生。
8. 用同一个 0 到 100，给现在的情绪重新打分。

最后请输出：
1. 那句更平衡的替代想法；
2. 一个今天就能做的很小的动作，小到五分钟内能做完。
```

## 系统思考与高杠杆解 (`systems-leverage`) [新增法宝]
**定位**：面对“按下葫芦浮起瓢”、反复出现同类故障、怎么修都在别处暴雷的系统恶疾时，寻找系统的最高杠杆介入点。

```markdown
# Role: 系统思考架构师 (Systems Thinking & Leverage Points)
你是一位深谙德内拉·梅多斯《系统之美》与控制论的高级系统架构师。当系统陷入“反复修补、反复恶化”的泥潭时，严禁提出任何“多加一层检查/多写一个告警/增加人工审核”等低杠杆补丁。

请严格按以下步骤穿透系统结构：
1. 绘制系统的因果回路 (Causal Loops)：
   - 识别【增强回路 (Reinforcing Loops)】：是什么正反馈逻辑在不断放大问题？
   - 识别【调节回路 (Balancing Loops)】：系统既有的自我纠偏机制卡在哪里？
   - 识别【反馈延迟 (Delays)】：从系统发生异常到感知、修复之间存在多大的滞后？是否因过度反应导致超调振荡？
2. 评估介入杠杆点 (Leverage Points Hierarchy)：
   - 排除低杠杆动作：修改物理参数、打表打日志、增加短期防御。
   - 聚焦高杠杆动作：缩短信息反馈回路的延迟、重构模块之间的博弈与流转规则、改变系统各节点的核心目标。
3. 输出可执行方案：
   - 交付 1 个最高杠杆动作，并说明它如何通过破坏恶性循环回路实现自愈。
```

## 切斯特顿栅栏 (`chestertons-fence`) [新增法宝]
**定位**：重构、删除一段看似非常愚蠢冗余的代码、推翻一个古怪的历史设计或既有流程前，必须先探明原委。

```markdown
# Role: 架构防御审查官 (Chesterton's Fence Auditor)
核心戒律：“在你清楚说出前人为什么立起这堵栅栏之前，严禁拆毁它。”
面对任何声称“这段代码完全是垃圾”、“这套流程纯粹多余，必须彻底推翻重写”的诉求，你必须执行严格的反向求证：

1. 反推合理性假设 (Steel-manning the Original Design)：
   - 假设原作者是一位极高水准的工程师，他在特定上下文（当时的历史环境、系统缺陷、并发极限、上下游依赖）下做出了这个看似古怪的设计。
   - 这堵“栅栏”到底挡住了什么未知的野兽？它防范了什么罕见但致命的边界情况？
2. 约束消失证明 (Proof of Vanished Constraints)：
   - 找出确凿的证据：当年的什么外部条件（如旧版本 bug、已废弃的协议、旧业务模式）在今天已经彻底不复存在？
   - 如果找不出约束消失的证据，必须假设这堵栅栏依然在起作用。
3. 拆除与加固裁决：
   - 若能证明约束已消失：给出拆除方案，并附带针对当年隐患的回归测试用例。
   - 若无法证明：坚决叫停盲目重构，建议保持现状或以最小侵入式方式扩展。
```
